## 二、与 4090 那次的关键不同 + 踩的坑

### 裸机路径（vs 4090 的 Docker）

这台是 SGLang template（容器），不能再嵌套 Docker，所以不用 `docker compose`，改为：

```bash
# 1) 网关：本地 Mac 交叉编译成 linux 静态二进制，scp 上去（容器没装 Go）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o sglang_gateway ./gateway-go
# 2) SGLang：直接用容器预装的，python3 -m sglang.launch_server ...
# 3) demo：GATEWAY_URL=http://localhost:8081 python3 examples/xx_demo.py
```

### 踩的坑

| 坑 | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| **① 首台机器 GPU wedged** | 某张 GPU 报 `cudaErrorDevicesUnavailable`，杀进程后仍无法用 | 同时初始化多个 SGLang 时的偶发竞争，被杀进程留下僵死 CUDA 上下文；容器内 `nvidia-smi -r` 报 **Insufficient Permissions**，无法 reset | **换一台机器**（本记录用的是第二台，4 卡全部 CUDA 自测通过后才开跑） |
| **② 40GB 卡 OOM** | `torch.OutOfMemoryError`，SGLang 实例崩溃 | `--mem-fraction-static 0.85` 对 **40GB 卡太高**（SGLang 主进程 + 辅助进程合计超 40GB）；80GB 机器不会 | 降到 **`--mem-fraction-static 0.75`** + `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` |
| **③ 8080 被占** | 网关起不来 | Vast template 的 Jupyter 占了 8080 | 网关改用 **8081**，demo 用 `GATEWAY_URL=http://localhost:8081` |
| **④ NVLink 正向差别** | —— | 4090 无 NVLink，TP/EP 的 NCCL P2P 不稳，当时被迫加 `NCCL_P2P_DISABLE=1`（变慢） | **A100 有 NVLink，绝不加这个**——让 All-Reduce/All-to-All 走 NVLink，这正是加速来源 |

> DP 的 4 个实例改为**错开 15s 启动**（避免坑①那种同时初始化竞争）；实验间清理改为**脚本内循环 kill 直到 GPU 显存清空**（前台手动 kill 常被网络瞬断打断）。

### 详细过程（按时间顺序）

**第一台机器（4× A100-SXM4-80GB）— 因 GPU wedge 放弃**

1. 连接体检：`nvidia-smi` 4× A100、`topo -m` 显示 NVLink，`docker` 可用（原以为走 Docker）。
2. 起 DP 时同时初始化 4 个实例 → **GPU 2 报 `cudaErrorDevicesUnavailable`**，被杀后 GPU 2 显存 0 但仍无法 `set_device`（僵死 CUDA 上下文）。
3. `nvidia-smi -r -i 2` → **`Insufficient Permissions`**（非特权容器不能 reset GPU）。用户在控制台 **Stop→Start** 后，GPU 2 **依旧坏**（干净容器、缓存被清空仍失败）→ 判断该物理卡/主机有问题，**换第二台机器**。

**第二台机器（4× A100-SXM4-40GB，NVLink NV12）— 全部跑通**

4. 体检：**4 张卡 CUDA 自测全部 OK**（这次上机先逐卡测过才开跑），SGLang 0.5.15.post1 预装，`/workspace` 盘 99G，`/dev/shm` 251G。发现这是 **SGLang template（容器），不能 Docker-in-Docker** → 改**裸机路径**。
5. 准备：Mac 上交叉编译网关（`GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`）→ `scp` 到机器；`rsync` 仓库；`pip install requests`。
6. **DP 首次失败（坑②）**：`--mem-fraction-static 0.85` 对 40GB 卡太高，一个实例 `torch.OutOfMemoryError`（GPU 只剩 209MB）。→ 全脚本降到 **0.75 + `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`**。补起挂掉的那个实例后 **DP=4 成功：P50 921ms**。
7. **TP=4**：脚本内加**健壮清理**（`nvidia-smi --query-compute-apps=pid | xargs kill -9` 循环直到 GPU 显存清空），单实例 `--tensor-parallel-size 4`（不加 `NCCL_P2P_DISABLE`）→ **成功：P50 2754ms**。
8. **EP=4（坑③④）**：
   - `--enable-prefix-caching` 早在 4090 就删了；EP 用 `--ep-size 4`（新版 SGLang 参数）。
   - **HF 缓存在 `/workspace/.hf_home`（Vast template 设的），不是 `~/.cache`** → 脚本里清缓存删错路径，盘被 Qwen32B 撑满到 16G，MoE 下载卡死。从**正确路径**删 Qwen32B/Llama 腾出 87G。
   - 我边杀边重启，导致**多个下载进程竞争、把 MoE 的 `.incomplete` 分片搞坏死锁**（卡在 11G）。改用换名的 `ep_master.sh`（避免 `pkill` 自匹配）杀光重复 → **删掉损坏分片从头干净下载** → **成功：P50 846ms**，`[TP0 EP0]~[TP3 EP3]` 确认。

> 命令层面的经验：① 40GB 卡 mem-fraction ≤ 0.75；② HF 缓存看 `echo $HF_HOME`；③ 长任务用 VM 上 detached 脚本（网络瞬断不影响）；④ `pkill -f` 会匹配到自己命令里的模式串（虚报计数），核数用 `ps -eo args | grep -c "[b]ash ..."`。

### 实验一：DP=4 数据并行（dp_demo，Llama-3-8B）

**命令**（裸机，错开启动 4 个单卡实例 + 网关 :8081）：

```bash
source /venv/main/bin/activate
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
MODEL=NousResearch/Meta-Llama-3-8B-Instruct
for i in 0 1 2 3; do
  CUDA_VISIBLE_DEVICES=$i python3 -m sglang.launch_server --model-path $MODEL \
    --port $((30000+i)) --host 0.0.0.0 --mem-fraction-static 0.75 --trust-remote-code &
  sleep 15    # 错开启动，避免同时初始化竞争
done
# 等 4/4 healthy 后启动网关（config 含 4 个节点，port 8081）
CONFIG_PATH=/root/dp_config.json ./sglang_gateway &
GATEWAY_URL=http://localhost:8081 python3 examples/dp_demo.py
```

## 四、A100 vs 4090 对照与结论

> 三列并看：**我们 4090 实测**、**我们 A100 实测（本记录）**、**README 原基准 A100**。

| 实验 | 4090 PCIe（我们实测） | **A100 NVLink（我们实测）** | A100（README 原基准） | 4090→A100 加速 | 通信量 |
| --- | --- | --- | --- | --- | --- |
| DP=4 | P50 1215ms，40/40，4.0× | **P50 921ms，40/40，4.0×** | P50 764ms | **~1.3×** | 无跨卡通信 |
| TP=4 | P50 4836ms，20/20 | **P50 2754ms，20/20** | P50 2422ms | **~1.76×** | All-Reduce / 层 |
| EP=4 | P50 1653ms，20/20 | **P50 846ms，20/20** | P50 827ms | **~1.95×** 🔥 | All-to-All / 层 |

**TTFT 对照（NVLink 对通信的影响最直观）**：EP long-prompt TTFT，4090 ~63ms → **A100 ~18ms**；All-to-All 在 NVLink 上 <1ms/层，在 PCIe 上 5~20ms/层。

**结论要点**：

1. **完美的 NVLink 递进规律**：**通信越重，NVLink 加速越大**——DP（无跨卡通信）**1.3×** → TP（每层 All-Reduce）**1.76×** → EP（每层 All-to-All）**1.95×**。这就是高速互联对推理的核心价值。
2. **A100 上不需要 `NCCL_P2P_DISABLE` 兜底**——4090 那个"延迟偏高 25~50%"的问题在 A100 上消失了，这一列是"干净"的 NVLink 数据（4090 因无 NVLink、P2P 不稳被迫走较慢的 PCIe 通信）。
3. 我们的 A100 数字与 README 原基准**同量级、方向一致**（921 vs 764、2754 vs 2422、846 vs 827）；略高是因为这台是 **40GB A100**（README 是 80GB）+ **SGLang 0.5.15**（README 0.5.10）+ mem-fraction 0.75。
4. 同一套代码、同一批模型，只换机器/互联——**这正是"并行策略 + 高速互联对推理延迟影响"的最好教学对照**：4090 PCIe（[实验记录.md](实验记录.md)）vs A100 NVLink（本记录），两份并看即成完整对照。
