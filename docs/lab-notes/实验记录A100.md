# 4× A100-SXM4 Deployment and Benchmark Report

This report records the follow-up deployment of the RadixGates upstream snapshot on a rented 4× A100-SXM4-40GB host. The objective was to verify the same DP, TP, and EP configurations on an NVLink platform and document the operational differences from the RTX 4090 run. It is not a controlled A/B study of NVLink versus PCIe.

**Run date:** 2026-07-27  
**Evidence:** [`sglang_parallelism_runs.csv`](../../benchmarks/results/real_gpu/sglang_parallelism_runs.csv) and [`real-gpu-results.md`](../real-gpu-results.md)  
**Related run:** [4× RTX 4090 deployment report](实验记录4090.md)

## Executive summary

- Completed DP=4, TP=4, and TP=4 + EP=4 on a 4× A100-SXM4-40GB host with NVLink visible as `NV12` in `nvidia-smi topo -m`.
- Completed every measured request: **40/40** for DP and **20/20** for both TP and EP.
- Observed P50 latency of **921 ms** for DP, **2,754 ms** for TP, and **846 ms** for EP in the tested configurations.
- Recovered from an unusable GPU on the first rented host, a 40 GB startup OOM, an occupied gateway port, and competing model-download processes.
- The A100 configuration was faster than the RTX 4090 configuration for all three matched modes, but multiple software and deployment variables changed. The results do not isolate NVLink as the sole cause.

## Project evolution and scope boundary

This run used the delivered gateway preserved at `upstream-snapshot`. It predates the reliability upgrade on `main`, so it validates SGLang deployment and DP/TP/EP execution rather than the later circuit breaker, active probes, bounded-load routing, admission queue, retry policy, and observability changes.

Those later capabilities have their own failure-injection and real-engine evidence in the repository [README](../../README.md) and [`RELIABILITY.md`](../RELIABILITY.md). The two phases share a repository and operating context, but their measurements remain separate.

## Deployment environment

| Component | Configuration |
| --- | --- |
| GPU | 4× NVIDIA A100-SXM4-40GB |
| GPU topology | NVLink, `NV12` between GPU pairs in `nvidia-smi topo -m` |
| Driver / CUDA | 580.65.06 / CUDA 13.0 |
| SGLang | 0.5.15.post1, preinstalled in the host image |
| Execution boundary | Non-privileged hosted container; nested Docker unavailable |
| Gateway | Linux/amd64 static Go binary, port 8081 |
| Python environment | `/venv/main` |
| Model cache | Host-defined `HF_HOME` under `/workspace` |

The gateway was cross-compiled before transfer because Go was not installed on the rented host:

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -o sglang_gateway ./gateway-go
```

SGLang workers then ran directly in the provided environment rather than through Docker Compose.

## Host qualification

The first rented 4× A100 host was rejected after one GPU remained unavailable with `cudaErrorDevicesUnavailable`. The environment did not grant permission to reset the device, so the exact host-level cause could not be isolated safely. The replacement host was accepted only after per-GPU CUDA checks and topology inspection passed on all four devices.

For DP, worker startups were staggered by 15 seconds to reduce simultaneous initialization pressure:

```bash
for i in 0 1 2 3; do
  CUDA_VISIBLE_DEVICES=$i python3 -m sglang.launch_server \
    --model-path NousResearch/Meta-Llama-3-8B-Instruct \
    --port $((30000+i)) --host 0.0.0.0 \
    --mem-fraction-static 0.75 --trust-remote-code &
  sleep 15
done
```

## Measured results

Each row is one completed run from the original demo harness. Latency percentiles cover successful requests.

| Mode | Success | P50 | P95 | TTFT evidence | Memory evidence |
| --- | ---: | ---: | ---: | --- | --- |
| DP=4 | 40/40 | 921 ms | 1,749 ms | warm 31.1–62.6 ms; first request 228.2–419.5 ms | 26.1–32.1 GB per worker GPU |

The high first-request TTFT values in the DP row likely include engine warm-up and should not be compared directly with the RTX 4090 first-request numbers.

## Deployment incidents and corrective actions

| Symptom | Diagnosis | Corrective action | Result |
| --- | --- | --- | --- |
| One GPU remained unavailable after process cleanup | Host-level device state could not be reset from the non-privileged environment | Rejected the host; qualified a replacement before downloading models | All four GPUs passed CUDA checks on the replacement |
| DP worker failed with `torch.OutOfMemoryError` | `--mem-fraction-static 0.85` left insufficient headroom on 40 GB cards | Reduced to `0.75`; enabled `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | Four workers started successfully |
| Gateway could not bind port 8080 | The host image's Jupyter service already owned the port | Moved the gateway to 8081 and supplied `GATEWAY_URL` explicitly | Client scripts reached the intended gateway |
| MoE checkpoint download stalled | Multiple download processes competed for partial files; cleanup initially targeted the wrong cache path | Inspected `HF_HOME`, stopped duplicate processes, removed incomplete shards, restarted one download owner | EP model completed and four ranks started |

## Parallel-mode startup

Tensor parallelism:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 python3 -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-32B-Instruct \
  --port 30000 --host 0.0.0.0 \
  --tensor-parallel-size 4 \
  --mem-fraction-static 0.75 --trust-remote-code &
```

Tensor plus expert parallelism:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 python3 -m sglang.launch_server \
  --model-path Qwen/Qwen1.5-MoE-A2.7B-Chat \
  --port 30000 --host 0.0.0.0 \
  --tensor-parallel-size 4 --ep-size 4 \
  --mem-fraction-static 0.75 --trust-remote-code &
```

No `NCCL_P2P_DISABLE` override was used in the A100 run.

## Cross-platform observation

| Mode | RTX 4090 configuration P50 | A100 configuration P50 | Observed ratio, 4090 / A100 |
| --- | ---: | ---: | ---: |
| DP=4 | 1,215 ms | 921 ms | 1.32× |
| TP=4 | 4,836 ms | 2,754 ms | 1.76× |
| TP=4 + EP=4 | 1,653 ms | 846 ms | 1.95× |

The larger observed gap in communication-heavy modes is consistent with the topology difference, but the comparison is confounded:

| Variable | RTX 4090 run | A100 run |
| --- | --- | --- |
| SGLang | 0.5.16, CUDA 12.9 runtime image | 0.5.15.post1 |
| Driver / CUDA | 575.51.03 / up to CUDA 12.9 | 580.65.06 / CUDA 13.0 |
| Deployment | Docker Compose with `ipc: host` | Direct processes in a hosted container |
| GPU memory | 24 GB | 40 GB |
| NCCL P2P for TP/EP | Disabled after initialization failure | Enabled |

Therefore, the ratios establish that the complete A100 configuration was faster in these runs; they do not measure an isolated NVLink speedup.

## Operating conclusions

- Qualify every rented GPU before model transfer; replace a host when device state cannot be reset or diagnosed within the environment boundary.
- Treat memory fraction as a deployment parameter, not a portable constant. The 40 GB host required headroom below 0.85.
- Discover cache location from the environment rather than assuming `~/.cache/huggingface`.
- Allow one owner per large checkpoint download and make recovery from incomplete shards explicit.
- Keep long startup and benchmark work in detached host-side scripts so client connectivity cannot interrupt it.
- Record engine, driver, deployment, topology, and NCCL overrides next to every performance number.

## Interpretation limits

- One run was retained per cell; no confidence intervals were computed.
- The 4090 and A100 hosts did not share an identical software or deployment stack.
- No direct interconnect microbenchmark was collected, so per-layer communication time is not claimed.
- Functional reference workloads are not evidence of a named customer deployment.

For the normalized data and the controlled-rerun plan, see [`real-gpu-results.md`](../real-gpu-results.md).
