## 一、机器环境（Vast.ai VM）

- **连接方式**：先加载密钥，再 SSH 连接（`-L` 把网关 8080 端口转发到本地）：

```bash
ssh-add ~/.ssh/id_ed25519
ssh -p 22 root@203.0.113.10 -L 8080:localhost:8080
```

- **硬件**：
  - 4× NVIDIA RTX 4090（每卡 24GB，实际可用约 23GB）
  - 卡间互联 **PHB（PCIe，不是 NVLink）**
  - 46 CPU 核；197GB 内存；126GB 系统盘（初始 119GB 空闲）
- **软件**：
  - Docker 28.1.1；docker compose v2.35.1
  - NVIDIA 驱动 575.51.03（**最高支持 CUDA 12.9**）
  - git / python3 / curl 均已预装；端口 8080 空闲（无 Jupyter 抢占）
- **说明**：这是能跑 Docker 的 VM 实例（不是普通受限的 container template），所以走 Docker 路径。

## 二、按时间顺序的操作步骤（含问题与解决）

### 第 0 步 — 连接 + 只读环境体检

- 加载密钥并 SSH 连上。
- 确认硬件与软件版本：

```bash
nvidia-smi          # 确认 4× RTX 4090
docker version      # 确认 Docker 28.1.1
docker compose version   # v2.35.1
nvidia-smi topo -m  # 互联方式 → PHB (PCIe)
```

- GPU 在 Docker 里直通测试（4 张 GPU 可见 ✓）：

```bash
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi -L
```

- 端口 8080 空闲。

### 第 1 步 — 传代码 + 构建网关镜像

- 用 tar over ssh 把本地清理后的仓库传到 VM 的 `/root/RadixGates`。
- 后台预拉 SGLang 镜像（大文件，边下边干）：

```bash
docker pull lmsysorg/sglang:latest   # 后台运行
```

- 构建网关镜像（纯 Go、无 CGO，镜像仅 **95MB**）：

```bash
cd /root/RadixGates && docker build -t unicoregpu2020/radixgates:latest .
```

- 安装 demo 脚本依赖：

```bash
pip3 install requests
```

- **关键点**：所有 compose 共享一个 `hf_cache` 卷（挂到 `/root/.cache/huggingface`），所以同一个模型**只下载一次**、跨实验复用。

### 第 2 步 — 首次启动 DP=4，遇到【问题①】

- 启动命令：

```bash
MODEL_PATH=NousResearch/Meta-Llama-3-8B-Instruct docker compose -f docker-compose.dp.yml up -d
```

- 报错（容器起不来）：

```
nvidia-container-cli: requirement error: unsatisfied condition: cuda>=13.0, please update your driver to a newer version, or use an earlier cuda container: unknown
```

- **原因**：`lmsysorg/sglang:latest`（2 天前构建）是按 **CUDA 13.0** 编译的，但本机驱动最高只支持 **CUDA 12.9**。
- **解决①**：换用 CUDA 12.9 的镜像，并在本地打成 `latest`（这样 compose 文件不用改）：

```bash
docker pull lmsysorg/sglang:v0.5.16-cu129-runtime
docker tag lmsysorg/sglang:v0.5.16-cu129-runtime lmsysorg/sglang:latest
docker image prune -f   # 清掉用不了的 cu130 悬空镜像，回收约 30GB
```

- **备注**：Docker Hub 上 SGLang 0.5.10（论文用的版本）只剩 cu130 镜像，没有 cu12x，所以没法既用 0.5.10 又匹配 12.9 驱动 → 改用 v0.5.16-cu129。

### 第 3 步 — 再次启动 DP=4，遇到【问题②】

- 容器这次能启动，但立刻崩溃重启，日志报：

```
sglang serve: error: unrecognized arguments: --enable-prefix-caching
```

- **原因**：新版 SGLang v0.5.16 **移除了 `--enable-prefix-caching` 参数**（RadixAttention 前缀缓存现在**默认开启**，不需要这个 flag）。而 compose 文件是照旧版 0.5.10 写的。
- **解决②**：从所有 compose 里删掉这个参数（功能不受影响，前缀缓存仍默认开）：

```bash
sed -i '/--enable-prefix-caching/d' docker-compose.dp.yml docker-compose.tp.yml docker-compose.ep.yml docker-compose.pd.yml docker-compose.pd-node.yml
```

### 第 4 步 — DP=4 启动成功（对应"实验三"）

- 重新 `up`，模型 Llama-3-8B 下载一次（约 16GB，写入共享缓存），4 个副本转 healthy，网关启动。
- 健康检查：

```bash
curl -s localhost:8080/health   # {"status":"ok","mode":"direct"}
```

- 运行 `python3 examples/dp_demo.py` → 结果见下方"实验三"。

### 第 8 步 — 首次启动 TP=4，遇到【问题③】

- 释放 PD 的 GPU 后，启动 TP=4（Qwen2.5-32B，单卡放不下需切 4 卡）：

```bash
docker compose -f docker-compose.pd.yml down            # 释放 GPU
docker volume rm radixgates_hf_cache                    # 清缓存腾盘
CUDA_VISIBLE_DEVICES=0,1,2,3 TP_SIZE=4 \
  MODEL_PATH=Qwen/Qwen2.5-32B-Instruct \
  docker compose -f docker-compose.tp.yml up -d
```

- **问题③ 多卡 NCCL 失败（TP=4 首次启动）**
  - **现象**：sglang-tp 容器反复重启（`RestartCount=24`），日志 `RuntimeError: NCCL error: unhandled system error`，发生在 `ncclCommInitRank`（4 卡建通信组时）。
  - **根因**：Docker 里多卡 NCCL 需要更大共享内存；且 RTX 4090 无 NVLink、PCIe 上 P2P 不稳。（DP/PD 都是单卡容器 `tp_size=1`，不触发跨卡 NCCL，所以之前没事。）
  - **解决③**：给 sglang-tp / sglang-ep 服务加 `ipc: host`，并加环境变量 `NCCL_P2P_DISABLE=1`、`NCCL_IB_DISABLE=1`。代价：All-Reduce/All-to-All 走较慢的共享内存通路，延迟略高（这解释了 TP/EP 延迟比论文高）。

    ```yaml
    # docker-compose.tp.yml / ep.yml 的 sglang 服务加：
    ipc: host
    environment:
      - NCCL_P2P_DISABLE=1
      - NCCL_IB_DISABLE=1
    ```

- 修复后 TP=4 启动成功 → 结果见下方"实验五"。

### 第 9 步 — 首次启动 EP=4，遇到【问题④】

- 释放 TP 的 GPU 后，启动 EP=4（Qwen1.5-MoE-A2.7B，Expert 分卡 + All-to-All）：

```bash
docker compose -f docker-compose.tp.yml down
docker volume rm radixgates_hf_cache
```

- **问题④ EP 参数被废弃（EP=4 启动）**
  - **现象**：sglang-ep 崩溃，`sglang serve: error: unrecognized arguments: --enable-expert-parallel`。
  - **根因**：新版 SGLang v0.5.16 用 `--ep-size N` 取代了 `--enable-expert-parallel`。
  - **解决④**：

    ```bash
    sed -i 's/--enable-expert-parallel/--ep-size 4/' docker-compose.ep.yml
    ```

- 修复后 EP=4 启动成功 → 结果见下方"实验六"。

### 补充说明（网络与磁盘）

- **网络说明**：跑 TP/EP 期间，从本地到 Vast.ai VM 的 SSH 连接多次间歇性瞬断（VM 一直在运行，是网络路径问题，非实例故障）；对策是把"等待 + 起网关 + 跑 demo"改成 **VM 上 detached 脚本 + 短命令轮询**，大模型下载/加载不受 SSH 断影响。
- **磁盘说明**：每个大模型实验前先清空 `hf_cache` 卷（`docker volume rm radixgates_hf_cache`）腾空间——Qwen2.5-32B ≈ 64GB、MoE ≈ 28GB，119GB 盘装不下全部模型。

## 六、A100 NVLink 对照（引用原基准，非本次复现）

> ⚠️ **本节数据来自项目原作者的基准**（`README.md` 主表 + `docs/benchmark_parallel_modes.md`），**不是本次在 Vast.ai 上重跑的**。因为 4× A100 SXM（NVLink）实例难租，这里直接引用原基准，用来展示 NVLink 相对 PCIe 的加速。若日后租到 4× A100 SXM，可用**完全相同的命令**独立复现这一列。

### 命令是否一样？——一样，只差一个 NCCL 参数

同一套 `docker-compose.{dp,tp,ep}.yml`、同样的 demo 脚本、同样的模型，换到 A100 上照跑。唯一区别：

| 项 | 4× RTX 4090（本次） | 4× A100 SXM |
| --- | --- | --- |
| 命令 / 模型 | `docker compose ... up -d` + `python3 examples/xx_demo.py` | **完全相同** |
| NCCL 配置 | 加 `NCCL_P2P_DISABLE=1`（4090 无 NVLink，兜底） | **去掉它**（让 NVLink P2P 生效） |
| 结果 | 延迟较高 | 延迟更低（NVLink 加速） |

### 为什么 A100 更快（原理）

- **All-Reduce（TP）**：带宽从 PCIe ~64 GB/s → NVLink 600 GB/s，每层同步开销从 ~20ms 降到 ~2ms。
- **All-to-All（EP）**：每次开销从 PCIe ~15ms → NVLink <1ms，long prompt 提升最明显（EP long TTFT 2.1×）。
- **DP**：无跨卡通信，加速纯来自 A100 单卡更强算力；两平台 DP 加速比都是完美 4.0×。

### 一个诚实的说明：本次 4090 实测 vs 原基准 4090

原基准的 4090 列（DP 1174 / TP 3851 / EP 1099ms）与我们本次实测（DP 1215 / TP 4836 / EP 1653ms）：

- **DP 很接近**（1215 vs 1174）——DP 无跨卡通信，不受 NCCL 影响。
- **TP/EP 我们偏高**（4836 vs 3851、1653 vs 1099）：因为我们这台 4090 必须加 `NCCL_P2P_DISABLE=1` 兜底、走较慢的 PCIe 共享内存 All-Reduce/All-to-All；原作者那台 4090 未受此限制。
- **A100 列不需要兜底**（NVLink P2P 正常），所以 A100 才是“干净”的通信数据。

因此：**本次亲手复现的是 4090 列（DP/TP/EP + PD + 流式 + 企业问答）；A100 列为引用原基准**。两列并看，NVLink 相对 PCIe 的 **1.3–1.6×** 加速一目了然。
